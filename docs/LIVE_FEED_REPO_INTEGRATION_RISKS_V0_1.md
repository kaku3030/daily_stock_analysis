# Live Feed — Repo-Level Integration Risks (Draft R1)

Status: **PLANNING ONLY — findings from repo inspection, not fixes.**
Per task scope: report risks, do not resolve them, and do not reopen the
frozen LiveFeed design. A repo mismatch is an implementation risk, not
automatically grounds for redesign.

| Risk | Severity | Affected files | Why it matters | When to address |
|---|---|---|---|---|
| Three independently-scoped health/fallback authorities with no documented boundary between them | **BLOCKER** | `data_provider/realtime_types.py:285` (`CircuitBreaker`), `src/services/stock_radar_v2/health.py:40` (`FallbackStateMachine`), `data_provider/market_data_adapter.py` (`MarketDataHealth.signal_permission`) | These are three genuinely different, legitimately separate authorities, not duplicates of one concept: `CircuitBreaker` is a call-outcome debounce keyed by source string; `FallbackStateMachine` is a provider-mode + `critical` state machine fired on connection/auth/subscription errors; `MarketDataHealth.signal_permission` is a per-fact AI-eligibility gate computed by `evaluate_health()`. **Do not unify or merge them** — each answers a different question at a different layer. The risk is that nothing in the repo currently *documents* which one is authoritative for which question, so a caller could see `FallbackStateMachine.mode=FALLBACK, critical=True` while the same moment's `Bar`/`Quote` still carries `signal_permission=NORMAL`, with no written rule for which one governs a given decision. A future LiveFeedController health signal would be a 4th, again legitimately scoped to its own question (data-plane LIVE truth, per frozen contract §5) — it must be added as a documented peer with an explicit authority boundary, not folded into or reconciled against the other three. | Before Phase 4 in the sequencing doc — write the authority-separation documentation before adding the 4th signal, not instead of adding it |
| `MarketDataAdapter` interface has no explicit streaming-provider capability boundary for unsubscribe | **BLOCKER** | `data_provider/market_data_adapter.py:153-191` | The abstract interface defines `subscribe()` but no `unsubscribe()`, no `connect()`/`close()`. This is not necessarily a defect requiring the shared ABC to gain `unsubscribe()` — the four existing adapters differ enormously in streaming capability already (two openly refuse to stream via `NotImplementedError`). The real gap is that the interface has no explicit way to declare or bound a provider's streaming-control-plane capabilities (subscribe-only vs. subscribe+unsubscribe vs. no streaming at all), so each adapter's actual capability is discoverable only by reading its source. A Futu adapter genuinely needs unsubscribe (confirmed provider behavior: unsubscribe doesn't drain callbacks — CASE 41 — and a minimum-hold rate limit exists server-side), and where that capability is declared/exposed (shared ABC extension vs. Futu-adapter-private, vs. a new capability-boundary concept) is an open decision, not settled anywhere in this pack. | Before Phase 4 (subscription reconciliation / command executor) |
| `MarketDataRouter.subscribe()` routes to primary only, by design | MAJOR | `data_provider/market_data_router.py:104-112`, enforced by `tests/test_market_data_router.py:133` | This is explicit, tested, intentional behavior ("never poll the fallback"), not a bug — but it means if Futu is ever configured as a *fallback* provider rather than primary, its streaming capability would be structurally unreachable through the router today. Any deployment plan that expects Futu-as-fallback-with-streaming needs a router change, which is out of scope here. | When deciding Futu's role (primary vs fallback) in the provider topology — not blocking for a primary-role Futu adapter |
| `RealtimeMarketDataService.ingest()` is fully synchronous, single `RLock` | MAJOR | `src/services/realtime_market_data.py:49-88` | `ingest()` assumes it is called inline on whatever thread delivers the bar — there is no queue, no async boundary today. Introducing a controller ingress queue (per the execution-model doc) means bars will arrive at `ingest()` from a *new* thread (the controller's consumption loop) rather than directly from the adapter's own callback thread as today's `AlpacaMarketDataAdapter`/`XtquantMarketDataAdapter` do. `ingest()`'s own `RLock` should make this safe as-is, but no test in `tests/test_realtime_market_data_service.py` currently exercises genuinely concurrent multi-thread `ingest()` calls (the `FakeAdapter` test double is called synchronously, single-threaded) — so this path is architecturally probably-fine but empirically untested for the concurrency pattern a controller would introduce. | Before Phase 3 (controller ingress queue wiring); add a concurrent-`ingest()` test as part of that work, not before |
| `aggregate_bars()` trusts each source `Bar.is_complete` flag with no independent verification | MAJOR | `data_provider/market_bar_builder.py:54-156`, specifically the `complete = ... and all(item.is_complete for item in ordered)` check (line ~109) | Futu's K_1M stream provides no completeness flag natively (confirmed — `time_key` is not completeness evidence). The Futu adapter itself must correctly *compute* `is_complete`/`is_closed` from its own interval-boundary-crossing logic (§A3 of the implementation spec) before handing bars to `ingest()`/`aggregate_bars()`. If the adapter gets this wrong, `aggregate_bars()` has no independent way to catch it — it will silently trust a wrong flag and produce a wrongly-`MISSING_BAR`-flagged or wrongly-complete 15m/1h bar. | Design-time for the Futu adapter's K_1M normalization logic (Phase 2); not a bug in `market_bar_builder.py` itself |
| No `unsubscribe()`/incarnation identity anywhere in current `Bar`/`Quote` models | MINOR | `data_provider/market_data_adapter.py:41-89` | Neither `Bar` nor `Quote` carries any field for `connection_generation`, `semantic_stream_key`, or `progress_identity_candidate`. The `ProviderEvent` envelope (§A1 of the implementation spec) is proposed as a *separate* type from `Bar`/`Quote`, deliberately not as an extension of them, specifically to avoid modifying the shared frozen dataclasses all four existing adapters and `ingest()`/`aggregate_bars()` depend on. This is a design choice worth flagging explicitly since it means the controller, not `Bar`/`Quote`, is the only place generation/incarnation identity is tracked — `Bar`/`Quote` remain "facts" the way they are today. | Confirm this separation holds up once the controller skeleton (Phase 3) is actually built — revisit only if it doesn't |
| Existing tests all assume synchronous adapter behavior | MINOR | `tests/test_realtime_market_data_service.py:36` (`FakeAdapter`), and equivalent fakes in `tests/test_xtquant_market_data_adapter.py`, `tests/test_pytdx_market_data_adapter.py`, `tests/test_existing_market_data_adapter.py`, `tests/test_alpaca_market_data_adapter.py` | None of these test doubles simulate a queue-delivered, cross-thread callback path. A future Futu adapter's own test suite will need new test infrastructure (not reuse of these fakes) to exercise the controller-ingress-queue boundary realistically — this is expected, not a defect, but worth budgeting for rather than assuming existing fakes are reusable as-is. | Test-authoring time for Phase 2/3, not now |
| `CircuitBreaker` could plausibly be reached for as connection-lifecycle authority, but isn't one | MINOR | `data_provider/realtime_types.py:285-330`, `_realtime_circuit_breaker`/`_chip_circuit_breaker` singletons at lines 443-454 | It has no concept of "connected", "subscribed symbols", or socket/subscription state — only call-outcome counters keyed by a source string. A future implementer under time pressure might be tempted to reuse it as connection-lifecycle authority since it's already there and has the right *shape* of API (`is_available`, `record_success`/`record_failure`); it is the wrong tool for that job (frozen principle 14 requires a genuine single-writer controller, not a call-outcome debounce). | Explicitly call this out in any onboarding/handoff for whoever builds the controller, so it isn't reached for by convenience |
| Existing `FutuFetcher` and any future Futu streaming adapter will coexist as two separate Futu integrations | MINOR | `data_provider/futu_fetcher.py:59`, future Futu streaming adapter | `FutuFetcher` is polling-only, uses the legacy `UnifiedRealtimeQuote` model, and is unrelated to `MarketDataAdapter`. A new Futu streaming adapter would be a second, structurally separate integration with the same vendor. This is not necessarily wrong (different concerns: fundamentals/polling vs. streaming), but nothing in the repo documents that split as intentional today — worth a short doc note once the adapter exists, so a future reader doesn't assume it's dead code or a duplicate. | Low priority; a documentation note once the adapter is built, not now |

No `SEVERITY: BLOCKER` item above requires the frozen LiveFeed design to
change — both BLOCKER-severity items are repo-side integration
questions (documenting the authority boundary between the three existing
health/fallback concepts, and where a streaming capability boundary for
unsubscribe lives in the adapter interface) that must be answered before
implementation starts, not architecture defects in the frozen contract
itself.
